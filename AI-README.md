## What this is

Story Suite is one SillyTavern extension for roleplay and story chats. It keeps the story's state (the scene, the bag, the
people, the clock, the world, a fight) as data next to the chat, shows it in a view of its own, and tells the model the parts
that matter on each reply. The reader's own words and the story stay in charge: state changes come from what the story says
(change lines the model writes at the end of a reply) or from the reader's own clicks.

This file is the reference for a developer, or a developer's coding agent, who writes a **module** (code that plugs into the
host) or a **pack** (a plain-data world or game). Read it first, then the pointers in each section. Every file and export
named in backticks is checked by the generator against the code, and the tables are read from the code, so they cannot go
stale; a sentence that is only prose is checked by the tests named beside it.

## Concepts

- **Chat state.** Everything the story knows lives in the chat store (`core/store.js`) as domains of plain JSON, one module
  owning each domain. Only that module's commands write it. State is saved with the chat (`core/persist.js`;
  `docs/dev/saves-and-persist.md`).
- **Replies carry their changes.** Each reply holds the receipts of the commands that ran on it. State at any point is the
  starting state plus the receipts of the replies up to there, so a swipe, a swipe back, a deleted reply in the middle, a
  rewind and a reload all give the same state as live play. This is the **replay == live** rule; `core/replay.js` and
  `docs/v2/REPLAY.md` hold the contract. A command whose result depends on something outside the state (the clock, another
  reply, a roll) either takes it from the receipt's seed (`ctx.rng`, `ctx.roll`) or records a guard that is checked again on
  replay.
- **Change lines and the `<Changes>` block.** The model ends a reply with one hidden block, `<Changes>` … `</Changes>`
  (`<Changes></Changes>` when nothing changed), with one short line for each change: `op kind Name[ — text][ | label: value]`.
  The first mark of a line says how (table below); the capture step (`core/capture.js`) hands each line to the module that
  owns its kind, which turns it into a command run with cause `story`. A line a module refuses is told to the reader as a
  Problem and changes nothing; the others still run. `docs/dev/capture-and-reread.md` covers Re-read, including an edited
  Re-read, and the optional extractor that repairs a reply with no block.
- **Commands and queries.** A command is the only way to change state; it runs in one transaction on the bus
  (`core/commands.js`) and either commits all of it as a receipt or none. A query reads state and never writes. Modules call
  each other's commands and queries by name (`ctx.call`, `ctx.query`), never each other's code. A command has a cause:
  `story` (a change line), `ui` (the reader's click, through `sdk.command`) or `system` (the host's own steps, such as a
  hook before a reply).
- **Prompt.** Each module may give a fixed text (static), a changing text (tail) and a budget; the host assembles them
  (`core/prompt.js`; `docs/dev/prompt-and-context.md`). The static part depends only on the code and the reader's feature
  switches, so it is byte-identical from reply to reply (the model's cache keeps it), and the whole static prompt is pinned
  by `tests/suite/static-prompt.golden.json`. A reply also ends with a fixed cue to write the `<Changes>` block
  (`core/turn/text-parts/closing-cue.js`).
- **Story-driven.** The reader acts through the story. The one door for a story action from the UI is the interaction port
  (`core/interaction.js`): a module declares an interaction kind (today only the fight board), the reader stages choices on
  its screen, code settles the outcome from a stored seed and those choices, and the narrator writes the next reply from a
  short settled note. The one policy of who may choose is `STORY_ACTION_POLICY` in `core/interaction/policy.js#STORY_ACTION_POLICY`:
  the reader chooses for their own character, and for every party member in a fight; anyone else is played by the kind's
  `auto` or left to the narrator. `docs/dev/interaction.md` has the lifecycle (open, stage, send, settle, carry) and what each
  turn event (swipe, regenerate, delete, rewind, reload, Re-read) does to it.
- **Features.** A module marks parts of itself with a feature id; the reader can switch the feature off. A feature that is
  off leaves no trace: no prompt text, no hooks, no cards, its queries answer `null` and its commands are refused.
- **Packs and data modules.** Content (places, lore, a cast, a calendar) comes from packs, plain data that code reads
  through queries. Small rule sets can also be written as data modules inside a game pack and run by the host
  (`modules/data-modules/`, `docs/v2/DATA_MODULES.md`); they need no code from you.

Kinds are the module's to name. The grammar line of each kind is part of the static prompt, so a new kind, or new wording of
an old one, changes the golden prompt: do it on purpose, with review.

## Rules

These hold for every change. The notes file for coding agents at the repo root has the full wording; CI enforces most of them.

1. **At most 450 lines per file**, tests included (aim for 300). Data and asset files (`.json`, `.md`, images, fonts) and vendored
   copies are exempt. `docs/merge/legacy-oversize.txt` may only shrink.
2. **One job per file, at most four exports.** A folder's index file or a facade that only re-exports may list more. Test
   files and test helpers under `tests/` are exempt from the export cap, not from the other rules.
3. **The code map stays current.** A new or moved file gets a sentence in `docs/codemap/jobs.json`, then `npm run codemap`.
   The maps and this file are generated; never edit them by hand, regenerate after merging.
4. **Replay == live.** A swipe, a swipe back, a middle delete, a rewind and a reload must reproduce the same state. A new
   command that writes state needs a test of each (see "Testing a module").
5. **Never edit a vendored copy** (anything under a `vendor/` folder).
6. **No model names** in code, commits, pull requests or docs.
7. **Reviews before merges; serialize changes to the same files.**
8. **The static prompt is pinned** by `tests/suite/static-prompt.golden.json`. Change it only on purpose (`WRITE_GOLDEN=1`),
   and NPC State wording needs the owner's approval.
9. **Story-driven.** No button performs a story action except through the interaction port. Bag management (use, equip,
   sell) is fine. `scripts/checks/core-module-refs.mjs` keeps RPG and fight words out of the core.
10. **Say NPC State**, not its old short name, in any text a person reads.
11. **The changelog is for players.** One line a bullet (about 200 characters), what a player sees or can do, no file
    paths, test names or job ids; the detail goes to `docs/history/CHANGELOG-detail.md`.
12. **A pack is data.** Nothing in a pack runs; the validator refuses anything unsafe, and code sets every number.

## How a module plugs in

A module is a definition object. A built-in module is a folder `modules/<name>/` (the core module, in `core/`, merges the
parts of scene, inventory, data modules and the RPG; Director and NPC State are listed in `core/modules-list.js#BUILTIN_MODULES`);
an outside extension registers its own with `sdk.registerModule(def)` after `await StoryBlock.ready`
(`examples/fishing/index.js` is the reference; the how-to is `docs/dev/writing-a-module.md`, and "Writing a plug-in module" below). The registry (`core/registry.js#createRegistry`) checks the definition when it
registers and refuses it, with a plain sentence, if it breaks a rule (`core/registry/registry-checks.js#definitionProblems`).
The definition names what the module owns; the host does the rest.

- **`id`, `name`, `version`.** The id is lowercase letters, digits, `.`, `_` or `-`.
- **`domains`.** The state the module owns: `{ initial(), validate(slice) }`, validate returning a list of problems. One
  owner per domain, and the initial state is plain JSON.
- **`commands`.** The module's writes, `type(ctx, payload)`, names are words joined by dots (the prefixes `capture.` and
  `module.` are the host's). A handler reads frozen copies (`ctx.read`), changes drafts of its own domains (`ctx.draft`), may
  call other modules' commands in the same transaction (`ctx.call`), takes randomness from `ctx.rng` or `ctx.roll` (never
  `Math.random`: the receipt's seed makes replay identical), claims a one-time key with `ctx.claim`, and returns
  `{ summary, data?, narrate? }`. `ctx.fail(code, message)` or any throw keeps nothing. A command may be `{ handler, internal: true }`
  (not callable from the view) or `prelude: true`.
- **`queries`.** `name(state, args)`: reads that other modules and the view may call; they answer `null` when the module or
  its feature is off. `replayQueries` names the ones a replay guard may ask (they must depend on state and arguments alone).
- **`capture`.** `kinds`: the change-line kinds the module owns, each with one `grammar` line for the prompt; and `apply(ctx, line)`,
  which runs a line as a story command (`line` is `{ op, kind, name, text, labels }`). A kind may be `display`, read for the
  reader alone.
- **`context`.** `static()`, `tail(view)` and `budget` (tokens) for the prompt, or a list of `parts`.
- **`hooks`.** Steps the host calls at fixed points: `beforeGenerate`, `afterCapture`, `canGenerate` and a few named ones
  (`docs/v2/SPEC.md` §6). They ask for `system` steps; they never write state themselves.
- **`settings`, `features`, `cards`.** What the module adds to Settings, the switches the reader can turn off, and the
  cards it shows under replies. (`tabs` are accepted but not drawn: the view draws its own fixed tabs. A plug-in's own `screens` and `widgets` open in the view's sheet, through the Party tab's
  `party.newCharacter` answer; nothing else draws a module screen. `docs/dev/ui-and-screens.md` top note, `docs/dev/writing-a-module.md`.)
- **`interactions`.** Kinds for the interaction port (`core/registry/registry-checks-parts/interaction-problems.js`: `version`,
  `title`, `feature`, `screen`, `limits`, `changes`, `ready`, `open`, `witness`, `validate`, `play`, `settle`, `note`, and optionally
  `actors`, `auto`, `opening`, `view`, `carry` with `next`, `marker`, `autoSend`).
- **`requires`.** `{ storyBlock: '>=2.0.0', peers: { 'story-director': '^2' } }`. A module whose peer is missing, of another
  version or off is dormant: registered, its names kept reserved, nothing else of it runs (`docs/v2/LIFECYCLE.md`).

### A minimal module

A counter of lantern oil: one domain, one command, one query, one change-line kind, a line in the prompt tail. The next
section tests it; both blocks are run by `tests/scripts/ai-readme-examples.test.js`.

```js module-example
export const lantern = {
  id: 'lantern', name: 'Lantern', version: '1.0.0',
  domains: { lantern: { initial: () => ({ oil: 3 }), validate: slice => (Number.isInteger(slice.oil) && slice.oil >= 0 ? [] : ['oil must be a whole number, 0 or more']) } },
  commands: {
    'lantern.burn'(ctx, { amount }) {
      const lamp = ctx.draft('lantern');
      if (amount > lamp.oil) ctx.fail('NO_OIL', 'The lantern has too little oil.');
      lamp.oil -= amount;
      return { summary: `The lantern burns ${amount} oil.`, data: { amount } };
    },
  },
  queries: { 'lantern.oil': state => state.domains.lantern.oil },
  capture: {
    kinds: { lantern: { grammar: '! lantern burn | amount: 1' } },
    apply: (ctx, line) => ctx.call('lantern.burn', { amount: Number(line.labels.amount ?? 1) }),
  },
  context: { static: () => '', tail: view => ({ lines: [`The lantern holds ${view.query('lantern.oil')} oil.`], optional: [] }), budget: 20 },
};
```

Rules of thumb for a new module:

1. Start from a small existing one, such as `modules/time` (read its header comment, then its parts) or `examples/fishing`.
2. Never reach into another module's files; call its commands and queries.
3. Keep each file to one job and at most four exports; a module's index file re-exports its parts.
4. Write the replay tests with the module (below).
5. Add its files to `docs/codemap/jobs.json` and run `npm run codemap`.

A module that owns an activity the reader plays (the fight board is the one built) declares an `interactions` kind and
registers a renderer for it in the view (`docs/dev/interaction.md`, "How the Suite view shows an activity"); it never adds a
button that performs a story action.

Detail: `docs/v2/MODULES.md` (layouts and decisions), `docs/v2/LIFECYCLE.md` (peers and restore), `docs/v2/EVIDENCE.md` and
`docs/v2/REPLAY.md` (guarded blocks), `docs/dev/prompt-and-context.md` (prompt budgets).

## Testing a module

The testkit (`testkit/index.js`) is a fake SillyTavern and a whole host on it, wired the way `core/boot` wires the real one
(registry, settings, store, command bus, SDK, turn). Import it by relative path from a test; never copy it. Its entries:
`createHost` (`testkit/host.js`), `createFakeModel` (script the model), `createFakeContext`, `aiMessage`, `userMessage`.

`const host = await createHost({ modules: [def] })` gives `host.send(text, reply)` (the reader's message and the reply the
model writes), `host.swipe(reply)`, `host.regenerate`, `host.turn.reread(index)`, `host.st.deleteMessage(index)`,
`host.st.swipeTo(index, n)`, `host.store.rebuild()`, `host.sdk` (`command`, `query`), `host.head()` and `host.close()`.
Passing `st: { chat, extensionSettings }` from another host builds a reload.

A reply is its story, then the block: `` `${text}\n\n<Changes>\n${lines.join('\n')}\n</Changes>` ``.

**Replay == live, as a test.** Every module that writes state pins the same five events: after each, the state equals what
live play gave, and a rebuild from the receipts equals it too.

1. send two replies, note the state;
2. `host.store.rebuild()` and compare (replay);
3. build a second host from a copy of the chat (reload) and compare;
4. `host.swipe(...)` the head, check the state, then `host.st.swipeTo(...)` back and check it returns;
5. `host.st.deleteMessage(middle)` and `host.turn.reread(head)` (an edited Re-read), then compare with a rebuild.

`tests/modules/inventory/bag-slot.test.js` is a real one. The block below does it for the lantern, with oil amounts chosen so no command can refuse; it is run as a test:

```js test-example
import test from 'node:test';
import assert from 'node:assert/strict';
import { createHost } from '../../testkit/index.js';   // the path depends on where the test sits: tests/modules/<name>/ needs ../../../
import { lantern } from './lantern.js';

const reply = (text, lines) => `${text}\n\n<Changes>\n${lines.join('\n')}\n</Changes>`;

test('lantern: replay equals live', async t => {
  const host = await createHost({ modules: [lantern] });
  t.after(() => host.close());
  const oil = () => host.sdk.query('lantern.oil');
  await host.send('Go on.', reply('Dark.', ['! lantern burn | amount: 1']));
  const middle = host.ctx.chat.length - 1;
  await host.send('Further.', reply('Darker.', ['! lantern burn | amount: 1']));
  assert.equal(oil(), 1);
  // replay: a rebuild from the receipts equals live
  host.store.rebuild();
  assert.equal(oil(), 1, 'a rebuild equals live');
  // reload: a second host on a copy of the chat
  const loaded = await createHost({ modules: [lantern], st: { chat: structuredClone(host.ctx.chat), extensionSettings: structuredClone(host.ctx.extensionSettings) } });
  t.after(() => loaded.close());
  assert.equal(loaded.sdk.query('lantern.oil'), 1, 'a reload equals live');
  // swipe, and back to the first try
  await host.swipe(reply('Darkest.', ['! lantern burn | amount: 2']));
  assert.equal(oil(), 0, 'the swipe replaced the first try');
  await host.st.swipeTo(host.ctx.chat.length - 1, 0);
  assert.equal(oil(), 1, 'back on the first swipe');
  // an edited Re-read of the head reply
  const head = host.ctx.chat.length - 1;
  host.ctx.chat[head].mes = reply('Darker, told again.', ['! lantern burn | amount: 2']);
  assert.equal((await host.turn.reread(head)).ok, true);
  assert.equal(oil(), 0);
  // a middle delete: the first reply's burn goes, the rest stays, and a rebuild agrees
  await host.st.deleteMessage(middle);
  assert.equal(oil(), 1);
  host.store.rebuild();
  assert.equal(oil(), 1, 'a rebuild equals live after the delete');
});
```

## Writing a plug-in module

A plug-in module is a SillyTavern extension of its own that links into Story Suite through the SDK. The long guide for people is
`docs/dev/writing-a-module.md`; the references are `examples/fishing` (a mini-game) and `examples/text-rpg` (a rules module: prompt,
Party tab, replaces the RPG). Copy their layout. Do not write a module for what a data module (Settings → Packs and trackers, no code) does.

**Files.**

```
manifest.json   { display_name, loading_order, requires: [], optional: [], dependencies: ["third-party/story_suite"], js: "index.js", author, version }
index.js        const host = globalThis.StoryBlock; host.ready.then(sdk => sdk.registerModule(myModule(sdk)))   (log one line if host.ready is missing)
src/module.js   re-exports the definition; src/module-parts/*.js hold its parts (definition, commands, queries, tail, settings, constants)
src/rules/      pure rules (no ctx, no DOM): easy to test with chosen numbers
tests/          node --test; tests/helpers/host.js wraps createHost from the testkit (copy it from examples/text-rpg/tests/helpers/host.js)
```

The extension lives in its own git repository with `manifest.json` at its root (SillyTavern's Install extension needs that). Import nothing from
Story Suite's files in the extension itself; take everything from `sdk`. The definition is checked at registration by
`core/registry/registry-checks.js#definitionProblems`; `registerModule` throws its sentence.

**Definition keys and shapes.** (`docs/v2/SPEC.md` §3, §4, §6, §13.)

- `id` lowercase `[a-z0-9._-]`; `name`, `version`, `description` text; `icon` `fa-…` (≤ 40 characters); `requires`, `capabilities` as above.
- `domains: { name: { initial(), validate(slice) → string[], counters?: ['wood', 'members/*/xp'], scratch?, deferred?, holders? } }`. Name starts with a
  letter, no `/` or `~`. `initial()` is plain JSON. One owner per domain.
- `commands: { 'mod.verb': (ctx, payload) => ({ summary, data?, narrate? }) }`, or `{ handler, internal?, prelude? }`; names are words joined by dots,
  never starting `capture.` or `module.`. Gate with `Object.assign(handler, { feature: 'mod.on' })`.
- `queries: { 'mod.name': (state, args, tools) => value }`; `null` while the module or its feature is off. Properties: `feature`, `fallback: true`.
- `capture: { kinds: { kind: { grammar: 'one line', aliases?, heads?, display? } }, apply(ctx, line) }`; `line` is `{ op, kind, name, text, labels }`.
- `context: { feature?, static(), tail(view) → { lines, optional }, budget }` (or `parts`). `view` has `state`, `query`, `feature`.
- `hooks: { beforeGenerate(view, info) → { commands: [{ type, payload }] } | null, afterCapture, canGenerate, … }`: they ask for steps, never write.
- `features: [{ id, label, describe, default, prompt?, needs?, presets?, replaces?: ['story-block.rpg'] }]`.
- `settings: { section: 'Page title', defaults, schema: { key: { type: 'bool'|'int'|'choice'|'text'|'list'|'profile', label: 'Section: Name', help?, feature?, max?, options?, form? } } }`.
  `form: 'prompt'` on a `text` field is the prompt editor (`builtin`: the default text, `max`: its length); empty means the built-in. Read with `sdk.settings(id)` or `ctx.settings(id)`.
- `widgets: { 'mod.name': { props, feature?, render(el, props, api) } }` (names start with the module id and a dot) and `screens: [{ id: 'mod/name', title, mounts: ['dialog'], feature?, template: '<ss-widget name="mod.name" data-props="{}"></ss-widget>' }]`.
  The view opens a plug-in's own screen in its bottom sheet (`api = { command, query, preview, commit, on, close }`); `tabs` are not drawn.
- `cards`, `interactions`, `headerControls`, `replayQueries` as in the section above; do not use `tabs`.

**`ctx` in a handler.** `read(domain)` (frozen), `draft(domain)` (own domains only), `call(type, payload)` (same transaction), `query(name, args)`,
`rng()`, `roll('2d6')`, `claim(key)`, `id(prefix)`, `absolute(domain, path)`, `unique`, `ifThere`, `feature(id)`, `settings(id)`, `time()`, `fail(code, message)`,
`cause`, `caller`, `receiptId`, `carrier`. Handlers are synchronous.

**Replay == live: do and do not.**

- Do take every random number from `ctx.rng()` / `ctx.roll()`; draw in a fixed order. Don't call `Math.random`, `Date.now()` or `new Date()`.
- Do list every number that moves in the domain's `counters`. Do call `ctx.absolute(domain, path)` when a command *sets* a number. Don't write
  an absolute number for something that moves by adding.
- Do keep per-item records and per-item counts in keyed maps (`{ [id]: … }`, `practice: { lore: 4 }`). Don't edit a list by position; appending at the end is fine.
- Do derive what follows from other state on each read (level from xp). Don't store a copy of it.
- Do keep per-reply bookkeeping under the reply's id (`ctx.carrier.sid`) or in the receipt's `data`, and list its top-level fields in `scratch`.
- Do claim one-time acts with `ctx.claim(key)`. Don't await, fetch, call a model or touch the DOM in a handler. Plain JSON only in state and `data`.
- A middle delete drops that reply's changes and replays the later ones on the new base; write commands that still make sense there (ids, not positions).
- Do give a command with a switch the same `feature`, answer `FEATURE_OFF` from commands and `null` from queries when it is off.

**Prompt.** `static` and each kind's `grammar` are byte-identical every reply of a chat: no names, counts, times or dice; new static text goes behind a feature.
`tail` carries per-reply facts, the line that must survive first, `optional` lines last. `budget` is tokens (about 4 characters each); ask for the least that works
(Fishing 20, Text RPG 600). Render compact text, never JSON.

**Party tab.** `party.actors` → `[{ id, name, pc? }]` and `party.newCharacter` → a screen id or `null` are plain queries; `rpg.sheet` (rows) and `party.levels`
(`[{ id, name, level, left }]`) are `fallback: true` because the built-in RPG owns them. A sheet row may carry `commands: { spend, skillEdit }` (command names). All answer `null`
while the module is off. Replacing the RPG: a feature with `replaces: ['story-block.rpg']`; active = own feature on **and** the replaced one off (`examples/text-rpg/src/module-parts/active.js#active`).

**Tests.** Use the testkit (`createHost({ modules: [def], settings: { features: { 'mod.on': true } } })`). Required: `definitionProblems(def)` is `[]` (`core/registry.js#definitionProblems`);
each command and each refusal; replay (`host.store.rebuild()`), reload (a second host on a copy of the chat), swipe and back (`host.swipe`, `host.st.swipeTo`),
a middle delete (`host.st.deleteMessage`), a Re-read (`host.turn.reread`); feature off; static bytes equal across two replies with different state.
Run `node --test "tests/*.test.js"` in the extension; in this repository run `npm run check` and the tests of the folders touched.

## Combat Rules v1 and the fight board

The fight board is the one interaction kind built (`story-block/fight`, declared in `modules/rpg/board/interaction.js`), and
Combat Rules v1 is the only engine (`modules/rpg/combat/`, entry `modules/rpg/combat/play.js#playBoard`). The narrator tells
the story and starts a fight by setting a foe slot; the reader stages each exchange on the Fight tab (for every party
member), and code plays every blow from a stored seed (`modules/rpg/combat/dice.js`, the port's `dice(seed, offset)`). The
narrator then gets a short settled note. There is no narrated fight, roll planner or rules chooser; `docs/dev/fight-board.md`
has the design (read its C11 paragraph first: the older sections describe the removed engine).

**Marks: new fights get the new rules, old fights replay as recorded.** A rule change that would move an old result is
switched on by a mark on the fight's setup, written when the fight opens (`modules/rpg/board/v1-kind.js`), stored with the
fight's receipt, and read back on replay. A fight opened before a mark has none and plays exactly as it did, so replay still
equals live. The marks today:

| Mark | What it does when set |
|---|---|
| `fleeIdle` | a member who picked nothing pays no stance in an exchange where the party flees and gets away |
| `xpRule` | how a win pays: absent, per group; `'each'`, 15 for each foe; `'each2'`, the same with a mob paying a quarter and a minion half (`modules/rpg/combat/rewards.js#winXp`) |
| `gearStats` | the stats of worn gear count in every roll and in the log (`modules/rpg/board/v1-kind.js`), read live like soak |
| `speedFull` | a Speed stance adds its full skill mastery to evasion, not half (`modules/rpg/combat/rolls.js#playerRoll`) |
| `soakWhole` | soak takes off only the whole points it adds up to, so a small hit through low soak is not cut by one (`modules/rpg/combat/damage.js#takeHit`) |
| `gearWear` | a decisive hit taken wears the body armour (else the shield) and a decisive miss wears the weapon, one step, and the narrator is told (`modules/rpg/board/v1-wear.js`) |

To change a combat rule: add a mark, write it where the setup is built, read it where the rule applies with the old
behaviour as the default, and add a test that an old setup (without the mark) still gives its recorded result and a new one
the new result. Never change a rule for old setups. A fight is also sized by code (the pre-check keeps a tier and cuts it to
at most 4 standard foes, or 3 of an elite group; extra foes come in a tier lower) and pays XP and practice in the settle
(`modules/rpg/board/v1-award.js`).

## NPC State and one-pass capture

NPC State (`modules/people`) keeps a dossier for each person in the story: role, look, mood, goal, status, where they are, memories,
relationships, abilities and keepsakes. Its module is `modules/people/module.js` (`PEOPLE_MODULE_ID`), registered last.

**One-pass capture** means the same reply that tells the story also carries the NPC State changes: no second model call per
reply. Its rules go into the static prompt under the key `story_suite_static_people` (byte-identical every reply, so the cache
holds; the golden test pins that key in the scenarios where the capture is on), and its context and reminder (who is in the
scene) go in their own system message at the very end of the prompt, depth 0 (`modules/people/runtime/runtime-injection.js`). The model writes people's changes as lines inside the same `<Changes>` block, `~ npc Name | mood: alarmed`,
`+ npc Name | role | look`, `~ npc Name | learns: …`, `~ memory Name | …`, and the capture step hands them to NPC State like any
other kind. The rules text is built by `modules/people/core/core-prompts-lines.js#buildLinesParts`. A line that is wrong is
refused alone; the others still run. The host knows the capture is on when that static key is set
(`core/turn/prompt-hooks.js`). A slower pass later fills in a person's full profile from several scenes.

NPC State wording is the owner's: do not change a sentence of its prompt without approval, and say the golden changed.

## The UI layer

The view is `ui/` (entry `ui/index.js`, started by `ui/entry/turn-on.js`). It reads state only through a port (it holds no
state of its own and calls no module's code to read or write the story; a selector may import a pure helper) and draws what the
port answers. The layers, from the engine out:

1. **The port** (`ui/port/`). `ui/port/contract.js#PORT_METHODS` is the whole surface: `view(name)`, `command(...)`,
   `preview`, `commit` and `on(event, fn)`; `checkPort` validates an implementation. `ui/port/sb-port.js#createSbPort` wraps the
   SDK: views come from injected selectors fed by SDK queries, actions pass through as commands with cause `ui`, and
   nothing throws. `ui/port/fake-port.js#createFakePort` is the same surface over fixtures, for view tests. A story action
   goes through the interaction port, never a plain command (rule 9).
2. **Selectors** (`ui/select/`). A selector turns the recorded answers of queries into a plain **view-model** (for example
   `ui/select/party.js#selectParty`, `ui/select/bag.js`), leaving a gap `null` instead of guessing.
3. **Contracts** (`ui/contract/`). Each view-model has a shape spec (`ui/contract/party.js#PARTY_SHAPE`, the others beside it);
   `ui/contract/shapes.js#checkShape` lists the mismatches by path. A selector's output is checked against its shape in
   tests, so a tab can trust what it draws.
4. **Tabs and sheets** (`ui/tabs/<tab>/`, `ui/sheets/`, `ui/card/`, `ui/settings/`, `ui/shell/`). A tab asks `port.view('party')`
   and draws the view-model with the DOM helper (`ui/kit/dom.js#h`); a tab holds no story logic and reads no state of its own.
5. **Styles** (`ui/css/`, one folder per area). The look follows the design tokens; a layout fix is checked in a real browser
   at phone and desktop width, then inside a replica SillyTavern, before it ships.

To add a screen: write the query in the module, a selector and a shape for its view-model, a fixture in `ui/fixtures/`,
the tab or card that draws it, and tests for the selector (against the shape) and the tab (against the fake port). Reply
cards under a reply, and the settings pages, follow the same path (`ui/port/reply-cards.js`, `ui/select/reply-card.js`,
`ui/chat/reply-cards.js`). Text a reader sees says NPC State, never the old short name. Detail: `docs/dev/ui-and-screens.md`
(its top note says which sections describe the removed view), `docs/v2/GUIDE.md` (the reader's view).

## How a pack is written

A pack is one JSON file (called pack.json inside a zip) of plain data: nothing in it runs. **Format 4** has two kinds, and
a pack says which with `"format": 4` and `"kind"`:

- a **world pack** holds a world: lore, places, routes, regions, a cast, markets, world events, templates, foes and items,
  and where and when the story starts (`start`: `world`, `date`, `place`);
- a **game pack** holds the rules of play: currency, calendar, weather, names, the player's start, an RPG section, data
  modules and meter presets.

A world may suggest a game (`recommends.game`); the reader picks one world and one game in Settings › Packs, and a world zip
may carry its game beside it as game.json. Older formats (3 and below) are refused with a pointer to the converter
(`scripts/packs/convert-3to4.mjs`); a newer format is refused with "update the suite".

The pack checker (`packs/validate.js#validatePack`) reads the file, refuses anything unsafe (script tags, unsafe URLs or CSS,
oversize values, unknown fields) and fills in defaults. Code still sets the numbers: a pack value passes through the rules
and caps. Problems come back as `{ code, path, message }`, each a plain sentence naming the path.

- Ids inside a pack are slugs (lowercase letters, digits and dashes). A route names its two places by name; `start.place`
  names a place by id; every reference is checked when the pack is installed. The full id of a record is `pack.<pack>/<slug>`.
- `requires.suite` is a version range checked against the suite's own version (`{ "suite": "^0.1" }`); `requires.capabilities`
  names what the pack needs the suite to provide.
- Content reaches modules only through queries (`packs.content`, `packs.start`, `packs.calendar`, `packs.economy` and the
  others listed in `docs/dev/packs.md`), so a module that finds no pack works from its defaults. A reader's own setting always
  wins over a pack's value.
- **Check a pack before you share it.** The authoring kit holds the field reference (`authoring-kit/reference/PACK-FORMAT.md`,
  `authoring-kit/reference/LIMITS.md`) and the checker you run on your own file: `node authoring-kit/check.mjs path/to/pack.json`
  (`authoring-kit/check.mjs#checkPack` and the Studio both call `packs/validate.js#validatePack`, so a pack that passes one passes the other).
  The kit's agent notes are `authoring-kit/AGENTS.md`.
- **Worked example.** `examples/packs/ersveil/pack.json` is a full world (Ersveil, with its conversion notes, `examples/packs/ersveil/CONVERSION-NOTES.md`, and portraits) and
  `examples/packs/ersveil-game/pack.json` is its game pack; `examples/packs/ersveil.zip` holds both. Field by field:
  `docs/v2/PACKS.md`, "Pack format 4".

When you add a field or kind to the format: the validator, the safety check, the limit, the docs and a test that a hostile
value is refused all change together.

### A minimal world pack

Two places, a road, one lore entry and a start; the checker prints OK for it (the test runs it). A place needs a `kind` that is
one of the engine's classes (`capital`, `city`, `town`, `village`, `outpost`, `site`, `none`) or mapped in `placeKinds`, and map units `x` and `y`:

```json pack-example
{
  "id": "tiny-world", "format": 4, "kind": "world", "version": "1.0.0",
  "name": "Tiny World", "author": "You", "description": "Two places and a road.",
  "requires": { "suite": "^0.1" },
  "content": {
    "places": [
      { "id": "the-ford", "name": "The Ford", "kind": "village", "x": 10, "y": 20, "note": "A shallow crossing." },
      { "id": "the-mill", "name": "The Mill", "kind": "outpost", "x": 40, "y": 25, "note": "A water mill." }
    ],
    "routes": [{ "from": "The Ford", "to": "The Mill", "kind": "road", "km": 6 }],
    "lore": [{ "title": "The Miller", "keys": ["miller"], "text": "The miller owes the ford-keeper a favour." }],
    "start": { "place": "the-ford" }
  }
}
```

### A minimal game pack

```json game-example
{
  "id": "tiny-game", "format": 4, "kind": "game", "version": "1.0.0",
  "name": "Tiny Game", "author": "You", "description": "Copper and silver, a two-month year.",
  "requires": { "suite": "^0.1" },
  "content": {
    "currency": { "name": "copper", "plural": "copper", "short": "c", "coins": [{ "name": "copper", "plural": "copper", "value": 1 }, { "name": "silver", "plural": "silver", "value": 10 }] },
    "calendar": { "months": [{ "name": "Frost", "days": 30 }, { "name": "Bloom", "days": 30 }], "era": "TY" },
    "start": { "money": 20 }
  }
}
```
