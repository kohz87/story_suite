## What this is

Story Suite is one SillyTavern extension for roleplay and story chats. It keeps the story's state (the scene, the bag, the
people, the clock, the world) as data next to the chat, shows it in a view of its own, and tells the model the parts that
matter on each reply. The reader's own words and the story stay in charge: state changes come from what the story says
(change lines the model writes) or from the reader's own clicks.

This file is the reference for a developer, or a developer's coding agent, who writes a **module** (code that plugs into the
host) or a **pack** (a plain-data world). Read it first, then the pointers in each section.

- Version `0.1.0`: one version number for the whole extension, written everywhere by `scripts/release.mjs`.
- Call the people module **NPC State** in anything a person reads. Its folder is `modules/people`.
- The code map is the way into the code: `docs/codemap.md` lists every file with its one job, its exports and its tests.
  `docs/dev/codemap.md` says how it is made. Never hand-edit a generated map.

## Concepts

- **Chat state.** Everything the story knows lives in the chat store (`core/store.js`) as domains of plain JSON, one module
  owning each domain. Only that module's commands write it. State is saved with the chat (`core/persist.js`;
  `docs/dev/saves-and-persist.md`).
- **Replies carry their changes.** Each reply holds the receipts of the commands that ran on it. State at any point is the
  starting state plus the receipts of the replies up to there, so a swipe, a swipe back, a deleted reply in the middle, a
  rewind and a reload all give the same state as live play. This is the **replay == live** rule; `core/replay.js` and
  `docs/v2/REPLAY.md` hold the contract.
- **Change lines.** The model ends a reply with short lines that say what changed. The first mark of a line says how
  (table below); the capture step (`core/capture.js`) hands each line to the module that owns its kind, which turns it into a
  command. A line a module refuses is told to the reader and changes nothing. `docs/dev/capture-and-reread.md` covers
  Re-read, including an edited Re-read.
- **Commands and queries.** A command is the only way to change state; it runs in one transaction on the bus
  (`core/commands.js`) and either commits all of it as a receipt or none. A query reads state and never writes. Modules call
  each other's commands and queries by name, never each other's code.
- **Prompt.** Each module may give a fixed text (static), a changing text (tail) and a budget; the host assembles them
  (`core/prompt.js`; `docs/dev/prompt-and-context.md`). The whole static prompt is pinned by
  `tests/suite/static-prompt.golden.json`.
- **Story-driven.** The reader acts through the story. The one door for a story action from the UI is the interaction port
  (`core/interaction.js`, policy in `core/interaction/policy.js`).

## Rules

These hold for every change. The notes file for coding agents at the repo root has the full wording; CI enforces most of them.

1. **At most 450 lines per file**, tests included (aim for 300).
2. **One job per file, at most four exports.** A folder's index file or a facade that only re-exports may list more.
3. **The code map stays current.** A new or moved file gets a sentence in `docs/codemap/jobs.json`, then `npm run codemap`.
   The maps and this file are generated; never edit them by hand, regenerate after merging.
4. **Replay == live.** A swipe, a swipe back, a middle delete, a rewind and a reload must reproduce the same state. A new
   command that writes state needs a test of each.
5. **Never edit a vendored copy** (anything under a `vendor/` folder).
6. **No model names** in code, commits, pull requests or docs.
7. **Reviews before merges; serialize changes to the same files.**
8. **The static prompt is pinned** by `tests/suite/static-prompt.golden.json`. Change it only on purpose, and NPC State
   wording needs the owner's approval.
9. **Story-driven.** No button performs a story action except through the interaction port. Bag management (use, equip,
   sell) is fine.
10. **Say NPC State**, not its old short name, in any text a person reads.

Commands: `npm test` runs every test group; `npm run check` runs the size check, the code map check and the syntax checks;
`npm run codemap` regenerates the maps and this file; `git diff --check` must be clean.

## How a module plugs in

A module is a folder `modules/<name>/` that exports one definition. The registry (`core/registry.js`) checks it when it
registers and refuses it, with a plain sentence, if it breaks a rule. The definition names what the module owns; the host
does the rest.

- **Domains.** The state the module owns: a name, an `initial()` and a validator. One owner per domain.
- **Commands.** The module's writes. A handler reads frozen copies, changes drafts of its own domains, may call other
  modules' commands in the same transaction, and returns a summary. If anything throws, nothing is kept.
- **Queries.** Reads other modules and the view may call. They answer `null` when the module is off.
- **Kinds.** The change-line kinds the module captures from a reply, each with its grammar and the command it runs.
- **Context.** `static`, `tail` and `budget` for the prompt.
- **Hooks.** Steps the host calls at fixed points (before a reply is generated, after one is captured, and a replay guard).
- **Settings, features and tabs.** What the module adds to Settings, the switches the reader can turn off, and the tabs or
  cards it shows. A feature that is off leaves no trace: no prompt text, no hooks, no cards.
- **Peers.** `requires` may name other modules it needs. A module whose peer is missing or off is dormant, with its names
  kept reserved.

Rules of thumb for a new module:

1. Start from a small existing one, such as `modules/time`, and read its header comment, then its parts.
2. Take the host's services from the SDK, never from SillyTavern directly; `docs/v2/PUBLIC-API.md` is the surface other
   extensions get.
3. Put a model call behind the SDK's model call (`core/model-call.js`) so profiles, queues and the safety net apply.
4. Write the replay tests with the module (swipe, swipe back, middle delete, rewind, reload).
5. Add its files to `docs/codemap/jobs.json` and run `npm run codemap`.

Detail: `docs/v2/MODULES.md` (layouts and decisions), `docs/v2/LIFECYCLE.md` (peers and restore),
`docs/v2/EVIDENCE.md` and `docs/v2/REPLAY.md` (guarded blocks).

## How a pack is written

A pack is one JSON file (called pack.json inside a zip) of plain data: nothing in it runs. It can carry a world (places, routes, lore, a cast,
events, factions), game settings (currency, calendar, weather, rules) and a starting state. The pack checker
(`packs/validate.js`) reads it, refuses anything unsafe (script tags, unsafe URLs or CSS, oversize values) and fills in
defaults. Code still sets the numbers: a pack value passes through the rules and caps.

- Ids are `pack.<pack>/<slug>`; references inside a pack are checked when it is installed.
- `format` says which pack format the file is written for. A newer format than the suite reads is refused with a plain
  message. This section describes the format the suite reads now (the table below).
- Content reaches modules only through queries (`packs.content`, `packs.start`, `packs.calendar` and the others listed in
  `docs/dev/packs.md`), so a module that finds no pack works from its defaults.
- Check a pack before you share it: the authoring kit (`authoring-kit/reference/PACK-FORMAT.md` and
  `authoring-kit/reference/LIMITS.md`) holds the field reference, and `authoring-kit/check.mjs` is the checker you run on your own file. The Pack
  Studio (below) runs the same checker in the browser.
- A worked example is `examples/packs/ersveil/pack.json`. Field by field: `docs/v2/PACKS.md`.

When you add a field or kind to the format: the validator, the safety check, the limit, the docs and a test that a hostile
value is refused all change together.

extension, shows each part read only and exports it again as a zip or JSON; editing is not built yet. These are its parts:
